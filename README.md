# Vendor Onboarding — CAP Learning Project

A hands-on project to learn SAP CAP development, Fiori Elements UI patterns, and (later) IAS + AMS authorization.

---

## What This Project Does

A simple Vendor Request management app where:
- **Requesters** create and view vendor onboarding requests
- **Reviewers** approve or reject requests with comments
- Role-based visibility: action buttons are disabled for non-reviewers

---

## What Was Built — Step by Step

### 1. CAP Project Scaffold
- `cds init` + `cds add sqlite`
- Single flat entity `VendorRequests` using `cuid` (UUID key) and `managed` (audit fields)
- `VendorStatus` enum type: `NEW`, `APPROVED`, `REJECTED`, `ADMIN_REVIEW`
- CSV seed data auto-loaded at startup

### 2. OData Service
- Single `VendorService` exposing `VendorRequests` as an OData v4 projection
- Computed field `statusCriticality` (integer) drives colored status badges in the UI
- Service path set via `@path: 'vendor-service'`

### 3. Fiori Elements UI
- Fiori Elements app created via SAP Fiori Application Generator (not `cds add fiori`)
- **Key learning:** UI annotations go in `app/vendor-requests/annotations.cds`, not in `srv/` — clean separation between service layer and UI layer
- List Report with filter bar (`@UI.SelectionFields`), table columns (`@UI.LineItem`), and status criticality coloring
- Object Page with four sections via `@UI.FieldGroup` + `@UI.Facets`: Vendor Info, Contact Info, Tax & Registration, Review Info
- `@UI.HeaderInfo` drives the Object Page title and subtitle

### 4. Approve / Reject Actions
- Two bound CAP actions: `approveRequest` and `rejectRequest`, each taking a `comment` parameter
- **Key learning:** `reject` is a reserved method in CAP's `ApplicationService` base class — always use a custom name
- **Key learning:** In Fiori Elements OData v4, bound actions in annotations use `ServiceName.ActionName` format, not `ServiceName.EntityName/ActionName`
- Actions return the updated `VendorRequests` entity — Fiori Elements automatically refreshes the Object Page with the returned data (no `@Common.SideEffects` needed)
- Action buttons placed via `@UI.Identification` on the Object Page header toolbar

### 5. Draft-Enabled Create Flow
- `@odata.draft.enabled` on the entity activates the Create button (List Report) and Edit button (Object Page)
- `before('CREATE')` handler auto-sets `status = 'ADMIN_REVIEW'` and `requestedBy = req.user.id` when a new request is saved

### 6. Mock Authentication and Role-Based Authorization
- Mock users defined under `[development]` profile in `package.json` — only active during `cds watch`, ignored in production
- `@requires: 'authenticated-user'` on the service forces login when the app loads
- `@restrict: [{ grant: 'INVOKE', to: 'VendorReviewer' }]` on actions — server-side enforcement
- `virtual isReviewer : Boolean` computed field populated in `after('READ')` handler using `req.user.is('VendorReviewer')`
- `@Core.OperationAvailable: isReviewer` on actions — disables Approve/Reject buttons for non-reviewers
- `@Capabilities.DeleteRestrictions: { Deletable: isReviewer }` — disables Delete for non-reviewers
- Review fields (`status`, `reviewedBy`, `reviewedAt`, `reviewerComment`) marked `@readonly` — non-editable in the form

### 7. Standalone App Router
- Added via `cds add approuter` — generates `app/router/` with `xs-app.json`, `default-env.json`, `package.json`
- **Key learning:** With npm workspaces, `@sap/approuter` is hoisted to root `node_modules/` — the start script must use `../../node_modules/@sap/approuter/approuter.js`
- `xs-app.json` has a single catch-all route forwarding all traffic to `srv-api` destination (CAP at `:4004`)
- `authenticationMethod: "none"` — App Router is a pure routing layer for now; CAP mock auth still handles login
- `forwardAuthToken: false` in `default-env.json` — no IAS token to forward at this stage
- `default-env.json` is git-ignored (`default-*.json` pattern in `.gitignore`) — never committed or deployed
- App Router runs on port `5001` (configured via `PORT=5001` in start script)
- **When IAS is added:** `authenticationMethod` changes to `route`, `authenticationType` per route changes to `ias`, and `forwardAuthToken` becomes `true`

---

### 8. MTA Deployment Descriptor
- `mta.yaml` generated via `cds add mta` — three modules: `vendor-onboarding-srv` (CAP), `vendor-onboarding` (App Router), `vendor-onboarding-db-deployer` (HANA HDI)
- HANA HDI container resource added via `cds add hana`; `[production]` db config added manually to `package.json`
- **UI deployment without HTML5 Repository:** Fiori app is bundled into the App Router directly
  - `npm run build:ui` — runs `ui5 build` in `app/vendor-requests/`, outputs to `dist/`
  - `npm run copy:ui` — copies `dist/` contents into `app/router/resources/vendor-requests/`
  - Both run automatically in `mta.yaml` `before-all` before `cds build --production`
- `app/router/xs-app.json` has two explicit routes:
  - `^/vendor-requests/(.*)$` → `localDir: resources` (static UI files)
  - `^/odata/(.*)$` → `srv-api` destination (CAP OData service)
- `app/router/resources/` and `app/vendor-requests/dist/` are git-ignored (build artifacts)
- **Key learning:** `@ui5/cli` must be in root `devDependencies` — npm workspaces hoists packages to root, and the UI5 CLI resolves its own module from the working directory upward

### 9. IAS Authentication

`cds add ams` was used (not `cds add ias`) because AMS depends on IAS — the command sets up both together:

**What `cds add ams` changes:**
- Adds `@sap/ams` (runtime) and `@sap/ams-dev` (local simulation) to `package.json`
- Upgrades `@sap/xssec` from v3 → v4 (required for IAS token validation)
- Sets `"auth": "ias"` under `[production]` in the CDS config
- Adds `vendor-onboarding-ams-policies-deployer` module to `mta.yaml`
- Adds `vendor-onboarding-ias` resource to `mta.yaml` with `authorization: enabled: true`

**Key learning:** AMS is not a separate BTP service. It is enabled by setting `authorization: enabled: true` on the IAS service instance in `mta.yaml`. Both share the same service binding.

**`xs-app.json` changes for IAS:**
- `authenticationMethod: "route"` (was `"none"`)
- `authenticationType: "ias"` added to both routes

**`mta.yaml` additions:**
- IAS bound to both `approuter` and `srv` with `credential-type: X509_GENERATED`
- `forwardAuthToken: true` and `forwardAuthCertificates: true` on the `srv-api` destination — the App Router passes the IAS token to the CAP backend over mTLS
- `deployed-after: vendor-onboarding-ams-policies-deployer` on the srv module — ensures policies are deployed before the service starts

### 10. AMS Authorization Policies

#### The `ams/` folder

`cds add ams` creates an `ams/dcl/` folder at the project root:

```
ams/dcl/
  schema.dcl               ← AMS attribute schema (auto-generated; user-editable)
  cap/
    basePolicies.dcl        ← auto-generated by cds build — DO NOT edit
  vendor/onboarding/
    reviewerPolicies.dcl    ← hand-written country-based policies
```

`cds build --production` copies these files into `gen/policies/dcl/`, which the `ams-policies-deployer` MTA module deploys to the AMS instance on BTP.

**Key learning:** The `cap/` subfolder is regenerated every build. Hand-written DCL must live in a separate package subfolder (e.g. `vendor/onboarding/`) that `cds build` copies but does not overwrite.

**Key learning:** The `ams/dcl/` folder is owned by root after `mbt build` (the MBT builder runs as root). If you need to add files, run `sudo chown -R $(whoami) ams/` first.

#### How `@restrict` annotations become policies

Adding `@restrict` at the **entity level** (not just on actions) is what triggers CAP's AMS plugin to generate `basePolicies.dcl`:

```cds
@restrict: [
  { grant: ['READ', 'CREATE'], to: 'VendorRequester', where: 'requestedBy = $user' },
  { grant: ['READ', 'UPDATE', 'DELETE'], to: 'VendorReviewer' }
]
```

`cds build` translates this into:

```dcl
POLICY "VendorRequester" {
  ASSIGN ROLE "VendorRequester";
}

POLICY "VendorReviewer" {
  ASSIGN ROLE "VendorReviewer";
}
```

Each `POLICY` + `ASSIGN ROLE` pair both defines the role and creates a named policy in AMS. In the IAS admin console, admins assign users to these policies to grant them the corresponding role.

**Key learning:** Action-only `@restrict` (on bound actions but not the entity) produces an empty `basePolicies.dcl`. Entity-level `@restrict` is required for policy generation.

**Key learning:** The `where: 'requestedBy = $user'` clause is a **CAP-level SQL filter** applied at OData query time. It does not appear in `basePolicies.dcl` — AMS handles role grant/deny, CAP handles row filtering on top.

#### Country-based instance policies

To restrict VendorReviewers to specific countries, two mechanisms are combined:

**1. Declare `country` as an AMS schema attribute** — via CDS annotation on the entity:

```cds
@ams.attributes: { country: (country) }
entity VendorRequests as projection on db.VendorRequests { ... }
```

`cds build` then generates `schema.dcl` with:

```dcl
SCHEMA {
  country: String
}
```

This registers `country` as a condition attribute usable in AMS policies.

**2. Write instance policies in `ams/dcl/vendor/onboarding/reviewerPolicies.dcl`:**

```dcl
POLICY "VendorReviewer_US" {
  ASSIGN ROLE "VendorReviewer" WHERE country = 'US';
}

POLICY "VendorReviewer_CA" {
  ASSIGN ROLE "VendorReviewer" WHERE country = 'CA';
}
```

**Key learning:** DCL string literals use **single quotes** (`'US'`). Double quotes (`"US"`) are interpreted as attribute references, not values — causing a deployment error.

**Key learning:** DCL files must be placed in a **package subfolder** (`vendor/onboarding/`), not at the root of `ams/dcl/`. The folder path defines the package; no `PACKAGE` declaration inside the file is needed or valid.

#### Testing authorization in BTP

After deploying, assign policies to users in the IAS admin console:

| Policy | Effect |
|---|---|
| `VendorRequester` | Can create and see own requests |
| `VendorReviewer` | Can see all requests, approve/reject/delete |
| `VendorReviewer_US` | VendorReviewer role, filtered to `country = 'US'` records only |
| `VendorReviewer_CA` | VendorReviewer role, filtered to `country = 'CA'` records only |

**Testing steps:**
1. Assign `VendorReviewer_CA` to a user → log in → only CA records visible
2. Switch to `VendorReviewer_US` → log in fresh (clear session) → only US records visible
3. Assign `VendorRequester` → Create button visible, can submit new request

**Key learning:** Multiple policies combine with OR logic. Assigning both `VendorRequester` and `VendorReviewer_US` to one user means they see their own requests (via Requester) AND US records (via Reviewer) — not just US. Keep roles separate in production.

### 11. Hiding the Create Button for VendorReviewers

The Fiori Elements Create button is a UI concern, not a backend concern — the backend already blocks CREATE for VendorReviewers via `@restrict`. The goal is a UX improvement.

**Why `@UI.CreateHidden: isReviewer` does not work:**
`isReviewer` is a row-level virtual field populated per record in `after('READ')`. The List Report's Create button has no record context — there is no row to evaluate the path expression against. FE4 cannot resolve `isReviewer` for a global toolbar button.

**Why automatic metadata capabilities do not work with AMS:**
In standard CAP (without AMS), the `$metadata` response is computed per user — a VendorReviewer without CREATE in their grant would get `Insertable: false`. With AMS auth, metadata is served statically; AMS enforces at the API level at runtime, not at metadata generation time.

**Solution: unbound function + FE4 controller extension**

Step 1 — Add an unbound function to `vendor-service.cds`:
```cds
function getCurrentUserInfo() returns { isReviewer: Boolean; isRequester: Boolean; };
```

Step 2 — Handle it in `vendor-service.js`:
```javascript
this.on('getCurrentUserInfo', req => ({
  isReviewer:  req.user.is('VendorReviewer'),
  isRequester: req.user.is('VendorRequester')
}));
```

Step 3 — Register a FE4 controller extension in `manifest.json` under `sap.ui5.extends.extensions`:
```json
"sap.ui.controllerExtensions": {
  "sap.fe.templates.ListReport.ListReportController#vendorrequests::VendorRequestsList": {
    "controllerName": "vendorrequests.ext.controller.ListReportExt"
  }
}
```

Step 4 — `webapp/ext/controller/ListReportExt.controller.js`:
```javascript
override: {
  onAfterRendering: function () {
    const oModel = this.base.getView().getModel();
    oModel.bindContext("/getCurrentUserInfo()").requestObject()
      .then(function (oResult) {
        if (oResult && oResult.isReviewer) {
          const oButton = this.base.getView()
            .byId("fe::table::VendorRequests::LineItem::StandardAction::Create");
          if (oButton) oButton.setVisible(false);
        }
      }.bind(this));
  }
}
```

**Key learnings for FE4 controller extensions:**

| Topic | Detail |
|---|---|
| File naming | Must be `ControllerName.controller.js` — `sap.ui.controllerExtensions` appends `.controller` when resolving the module |
| Registration key format | `BaseController#appNamespace::componentId` — the `#` qualifier scopes the extension to one specific page instance |
| `controllerExtensions` in routing target | Only works for ObjectPage, not ListReport — use `sap.ui5.extends.extensions` instead |
| `byId` with full DOM ID | `this.base.getView().byId()` already prepends the view prefix — pass only the local ID (`fe::table::...`) |
| Create button stable ID | `fe::table::VendorRequests::LineItem::StandardAction::Create` — inspect the DOM to verify |
| Lifecycle hook | Use `onAfterRendering` — button does not exist at `onInit` time |
